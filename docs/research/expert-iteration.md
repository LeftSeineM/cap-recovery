# 专家迭代：可复现失败驱动的 code as policy 改进

研究计划 B 方向“轨迹生成”的一部分：高密度场景中的专家轨迹由代码编写的专家（code as policy）生成，专家由 agent 迭代改进。这里写研究问题和实验设计；结果写在[实验台账](../experiments/20261025-expert-iteration-000002/README.md)，论文叙述放在单独的论文仓库。

## 研究问题

| 问题 | 可证伪假设 |
| --- | --- |
| Q1：失败复现与诊断工具能否提高 agent 迭代专家的效率？ | 从同一份起点代码出发，有工具时 agent 达到同一成功率所需的轮数和计算量更少，停滞或倒退的轮次更少。 |
| Q2：哪些工具起作用？ | 去掉帧快照复现或离线重解后，修复的正确率（改动在原失败入口上生效、且不降低完整任务成功率）明显下降。 |
| Q3：修复是否泛化？ | 只在共享技能中修根因、不为场景或 seed 调参时，改进在未参与修复的初态和新场景上保持。 |

## 方法

专家程序写在四层之上（专家、语义技能、原子技能与动作链、运动原语，见[专家](../specs/experts.md#分层)），按步骤保存检查点。迭代工具：

- 检查点重跑与 `--repeats`：区分偶然失败和结构性失败。
- 调用帧快照：用原参数、持物、规划世界和随机数从失败的技能入口重跑，复现原来的决策。
- 求解记录与离线重解：不启动仿真，重复求解当时的 IK 和规划问题，重新执行候选决策。
- 人工遥操：从失败处接手，检验步骤的检查是否写对。
- 技能入口回滚的有限重试（`--skill-attempts`）。

agent 的迭代流程：对失败分类，定位到机制；改共享技能；先在原失败入口上配对验证（原代码与修改各重复数次），再跑小规模完整任务筛查，最后按成功率选 seed 数跑完整批次（见[开发原则](../conventions/development.md#seed-数随成功率增加)）。

## 实验设计

- **主实验（Q1）**：从同一份起点 commit 出发，同一 agent 与预算，分“有工具”和“只有日志与录像”两组，各重复多次独立迭代。记录每轮的 commit、改动、完整任务成功率、agent 耗时和仿真计算量，比较成功率随轮数和计算量的曲线。
- **消融（Q2）**：逐项去掉帧快照复现、离线重解、`--repeats` 分类，其余同主实验。另统计每个候选改动在原失败入口上的配对结果与它对完整任务成功率的影响。
- **泛化（Q3）**：冻结代码后，在未参与修复的初态和新场景上测试；新场景包括 0001xx 的复杂场景。
- **指标**：完整任务成功率（附区间）、达到目标的轮数、agent wall time、仿真 CPU time、被否定的候选比例、倒退轮次。

## 现有证据与缺口

场景 000002 的迭代历史（[台账](../experiments/20261025-expert-iteration-000002/README.md)）：没有复现工具的前期多轮停滞，有工具后 4 轮从 266/300 提高到 295/300，独立初态 97/100。两段起点和规模不同，不能回答 Q1，需要主实验。

缺口：主实验与消融尚未进行；场景只有 000002、000003；部分历史批次从冻结副本运行，没有可取回的 commit。
