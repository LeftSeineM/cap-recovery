# 05 逐步编写专家

给编写专家的人。多步任务的专家（如场景 000002：开抽屉、取笔、关抽屉……）一次跑完整个流程时，后面步骤的失败要等前面都成功才看得到，每轮迭代都很慢。逐步编写的做法：先把第 1 步迭代可靠，用它成功的结束状态作为第 2 步的起始状态，再迭代第 2 步，依此类推。每一步的起始状态都来自真实执行，底盘位置、物体被放下的位置都和全流程一致，不需要手写。

前提：专家由步骤组成（`Step` 与 `run_steps`，见[步骤与检查点](../specs/experts.md#步骤与检查点)）。步骤之间手里不拿东西，每步的 `check` 检查结束状态是否满足下一步的起始条件。

迭代时的运行都是开发运行（`--dev`）：每次写到新目录 `runs/expert/<场景>/<机器人>/<专家编号>/<日期>-<时间>-<提交>-<机器人>-<专家编号>-layout<n>[-<标签>]/`，不会覆盖以前的结果，`--name` 给运行加一个标签。同一专家的开发运行可以在[浏览站点](../specs/expert-data.md#开发线浏览)里按 step 看搜索树。不带 `--dev` 的运行生成场景的数据 `data/scenes/<场景>/<机器人>/<专家编号>/<后端>/`，只能跑所有 seed 和所有步骤。

## 1. 迭代第 1 步

```bash
uv run python scripts/scenes/run_expert.py 000002 --physics isaac-cpu --dev --name step1 --steps 1 --jobs 20 --launcher '<调度命令>'
```

- 先用 20 个 seed 的初态（`--seeds 0:20`），改专家、重跑。每轮都是新目录，可以直接和上一轮对比。
- 失败按 `summary.json` 的 `failures` 和 `episodes/<seed>.json` 分析，找到根因再改通用代码，不为个别 seed 调参数（见[开发原则](../conventions/development.md#修根因不调参)）；录像用 `render.py 000002 --physics isaac-cpu --batch <data-dir>`，`<data-dir>`指`data/scenes/<场景>/<机器人>/<专家编号>/<后端>/`或者`runs/expert/<场景>/<机器人>/<专家编号>/<运行>/`。失败案例的查看方法见[第六章](06-failure-cases.md)。
- 成功率提高后增加 seed（约 90% 时 100 个，约 98% 时 300 个，见[开发原则](../conventions/development.md#seed-数随成功率增加)）。最后一批的 `checkpoints/step1.hdf5` 就是第 2 步的起始状态。

## 2. 下一步从检查点开始

```bash
uv run python scripts/scenes/run_expert.py 000002 --physics isaac-cpu --dev --name step2 --steps 2 \
    --from <第 1 步的批次> --jobs 20 --launcher '<调度命令>'
```

- 每个有第 1 步检查点的 seed 都从它开始：恢复状态、静置 0.2 s，只运行第 2 步。
- 迭代第 2 步时只改第 2 步用到的代码，同一份检查点可以反复使用。
- 读取时核对来源批次的机器人、专家编号、后端，以及检查点记录的步骤名是否等于当前专家的第 k − 1 步，不符就报错，防止插入或删除步骤后编号错位。来源目录只有一个检查点时（例如一个长期用例）可以省略 `--steps`，自动执行下一步。缺少身份标记的批次不能续跑，在当前代码上重跑。
- 每个批次都有各步的检查点，完整流程的批次也一样，所以也可以从任意一次完整运行的第 k − 1 步开始只跑第 k 步。从初态开始的批次另有 `step0.hdf5`（初态），`--steps 1 --from <批次>` 从它开始，与从初态开始相同。
- `summary.json` 的 `steps` 给出每步的成功率和逐步完成率（前面各步都成功才计入，分母是第 1 步的 seed 数），可以直接看出整条流程走到哪一步损失最多。

## 3. 什么时候合并步骤

逐步运行时，每一步只看到前一步成功的那部分状态。几步都可靠后（单步约 95% 以上），把它们合起来跑（`--steps 1-3`，或不带 `--steps` 跑完整流程），确认合起来的成功率约等于各步之积。明显偏低时，说明前一步虽然通过了 `check`，留下的状态对下一步不利（如底盘停的位置、物体放下的朝向），应该收紧前一步的 `check` 或修改前一步。

## 4. 改了共享技能后

`table_1000/experts/skills/` 的改动会影响所有步骤和场景。改动后：

1. 已经迭代完的步骤，用原来的检查点各跑一遍，确认成功率没有下降；
2. 场景 000000 跑完整流程（100 个 seed），和 main 比较。

检查点记录了生成它的提交。上一步的代码改了以后，它的检查点仍可用于迭代下一步，但最终数据要重新逐步生成或跑完整流程。

## 5. 接成完整轨迹

```bash
uv run python scripts/scenes/join_steps.py <第 1 步的批次> <第 2 步的批次> ...
```

同一 seed 在各批的轨迹按顺序接起来，每段截到下一批开始用的检查点；每条轨迹的 `parts` 属性记录各段的来源批次与提交。接好的轨迹默认写成场景的数据 `data/scenes/000002/isaac-cpu/`（整个替换），和一次跑完整流程得到的批次格式相同、只是生产方式不同，下游不需要区分；用 `render.py 000002 --physics isaac-cpu` 渲染。

接好的批次仍可以生成失败快照和离线重解（只含最后一段的记录，见[拼接](../specs/expert-data.md#拼接)）。
