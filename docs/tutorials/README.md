## 批量运行的通用参数

构建场景、生成轨迹、渲染、物理测试和机器人验收都是批量脚本，共用以下参数和行为：

- 工作（seed、测试、用例）分成 `--jobs` 个进程同时运行。本机运行时进程平均分到 `--gpus` 列出的显卡上（默认 `0`），`--jobs` 默认每张卡一个。
- `--launcher PREFIX` 把每个进程交给作业调度器，由调度器选卡，例如 `--launcher "srun --gres=gpu:1"`；这时不给 `--gpus`，`--jobs` 默认 16。
- 某个进程失败不影响其他进程。进程中途退出（显存不足、被调度器终止）而没有写出结果的工作自动重跑，次数由 `--retries` 设置（默认 1）；运行完但未通过的不重跑。重跑后仍有工作没有结果时，脚本以非零退出码结束。物理测试和机器人验收有用例未通过、构建场景有 seed 没得到有效初态时也是非零；生成轨迹时专家任务失败是正常结果，不影响退出码，成功率和失败列表看批次的 `summary.json`。
- `--seeds` 接受区间和单个 seed，区间左闭右开：`0:100` 为 seed 0–99，`20 64` 为两个 seed。
- 物理和规划主要在 CPU 上：不渲染时每个进程只占约 0.5 GB 显存，`--jobs` 可以是显卡数的几倍；渲染时显存占用大，每张卡宜少。每个进程启动约 20–35 s。
- 提交批次时，批量脚本在原检出的 `.local/batch-checkouts/` 下创建一份 detached worktree 冻结代码，所有工作进程（含排队和重跑的）都从这里启动；提交之后可以继续修改原检出的代码。工作区有未提交的改动（包括未被忽略的新文件）时，改动一起冻结：报告的 `commit` 带 `+dirty`，改动存为批次目录中的 `dirty.patch`，在这个 commit 上 `git apply` 即可还原。源码目录不是 Git 检出时直接在原地运行。冻结的检出沿用原检出的 Python 环境，`assets/`、`data/`、`runs/`、`outputs/` 指向原检出，所以运行期间不要重建资产或改初态；调度器上的机器要能访问原检出所在的文件系统。
- 批次正常结束、失败、Ctrl-C 或 SIGTERM 后自动删除固定检出，并行的批次各用各的目录。批次进程被强制杀死时检出会留下：启动日志中的 `CHECKOUT <commit> <路径>` 给出位置，`git worktree list` 也能列出；确认对应的工作进程已停止后，执行 `git worktree remove --force <路径>` 删除。
