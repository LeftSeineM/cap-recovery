## 批量运行的通用参数

构建场景、生成轨迹、渲染、物理测试和机器人验收都是批量脚本，共用以下参数和行为：

- `--jobs auto`（默认）按整批预计耗时划分进程，包含启动和环境加载。先取 `n10=floor(总秒数/600)`；`n10≥20` 时用 `min(100,n10)` 个 job，否则用 `min(20,max(1,floor(总秒数/300)))` 个。`--jobs N` 直接指定整批 job 数。专家按场景、机器人分区，每区至少一个 job；资产抓取允许同机器人、同后端的不同资产共进程。
- 本地并发数由 `--gpus` 的条目数决定（默认 `0`，即一个进程），job 数与并发数独立。`--launcher PREFIX` 将所有 job 一次提交给调度器，例如 `--launcher "srun --gres=gpu:1"`；此时不传 `--gpus`。
- 仓库默认在 `configs/batch.toml`，机器覆盖在 `~/.config/table-1000/batch.toml`，显式 CLI 优先；例如机器配置 `max_jobs = 10` 限制 auto。auto 分档作为整体覆盖。
- `--dry-run` 只写批次目录的 `plan.json`，列出分组、历史命中、预计最长耗时；随后可用同一输出目录正式运行。进程日志和分组 manifest 在批次的 `workers/<编号>-attempt<重跑次数>/`。
- 单元完成后立即原子写报告与 `runs/.batch-timing/` 耗时索引。估计依次采用该单元最近耗时、同组其他 seed 均值、本批已知单元中位数、入口声明的估计；启动和加载单独计入。缺报告及 `status=error` 按 `--retries`（默认 1）重跑，物理 `failed` 不重跑。其他单元照常完成，最终 summary 按每单元最后一次来源汇总。
- `--seeds` 接受区间和单个 seed，区间左闭右开：`0:100` 为 seed 0–99，`20 64` 为两个 seed。
- 物理和规划主要在 CPU 上：不渲染时每个进程只占约 0.5 GB 显存，`--jobs` 可以是显卡数的几倍；渲染时显存占用大，每张卡宜少。每个进程启动约 20–35 s。
- 提交批次时，批量脚本在原检出的 `.local/batch-checkouts/` 下创建一份 detached worktree 冻结代码，所有工作进程（含排队和重跑的）都从这里启动；提交之后可以继续修改原检出的代码。工作区有未提交的改动（包括未被忽略的新文件）时，改动一起冻结：报告的 `commit` 带 `+dirty`，改动存为批次目录中的 `dirty.patch`，在这个 commit 上 `git apply` 即可还原。源码目录不是 Git 检出时直接在原地运行。冻结的检出沿用原检出的 Python 环境，`assets/`、`data/`、`runs/`、`outputs/` 指向原检出，所以运行期间不要重建资产或改初态；调度器上的机器要能访问原检出所在的文件系统。
- 批次正常结束、失败、Ctrl-C 或 SIGTERM 后自动删除固定检出，并行的批次各用各的目录。批次进程被强制杀死时检出会留下：启动日志中的 `CHECKOUT <commit> <路径>` 给出位置，`git worktree list` 也能列出；确认对应的工作进程已停止后，执行 `git worktree remove --force <路径>` 删除。
