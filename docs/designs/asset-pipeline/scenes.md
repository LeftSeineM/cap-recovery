# 场景与专家轨迹规范

规定一个场景交付什么：场景源码、随机初始化与其他布局、专家程序、轨迹数据，以及验收方式。以场景 [scenes/000000](../../../asset_sources/scenes/000000/)（三抽屉柜与笔）、[scenes/000100](../../../asset_sources/scenes/000100/)（38 件物体的办公桌与十个布局）、[scenes/000101](../../../asset_sources/scenes/000101/)（62 件物体的电子维修工作台，含垃圾桶与桌面杂物）、[scenes/000102](../../../asset_sources/scenes/000102/)（30 件物体的梳妆台）和 [scenes/000103](../../../asset_sources/scenes/000103/)（按参考照片复刻的电子工作台，布局 0 即照片，垃圾桶在地上）为例，命令见[第四章](../../tutorials/04-scene.md)，各文件的位置见[资产布局](README.md#资产布局)。

[000003](../../../asset_sources/scenes/000003/README.md) 用通用技能把沿桌边随机摆放的笔放进抽屉。笔和柜子覆盖全部可用宽度，机器人从同侧桌边中央起步；初态按资产几何排除抽屉扫掠越界和笔挡住抽屉的布局，柜子朝向限制在工作侧 ±30°。它检验局部底盘挪动与操作，不要求绕桌导航；这些几何约束不预先筛选专家或IK成功率。

## 定位

- 每个场景只有一条高层指令：`tidy up the table`（整理好桌面）。专家按实际操作把轨迹分成子任务，每个子任务有一条英文指令（如 `open the bottom drawer of the cabinet`），数据同时提供高层与子任务两级指令。
- 每个场景有自己的专家程序，由大模型按本规范编写（code as policy）；场景也可以先只提供各布局的初态，专家程序以后补（如 000100）。场景和专家都不按任务类型命名，也不写成功判据（谓词）；轨迹好不好由人工抽查录像。自动化只做硬性检查和量化指标。
- 尽量使用现成框架：环境、状态读写、录制与重放用 Isaac Lab，运动规划求解器与抓取几何沿用 ManiSkill3 的写法。本仓库只补这些框架没有的部分：资产几何查询、初态检查、子任务记录。
- 生产分三步：构建场景（采样并检查初态，存下静置后的状态）、生成轨迹（从存下的初态运行专家）、渲染录像（按录制的状态）。

## 场景源码 `scene.py`

普通 Python 模块，不另设配置格式：

- **世界系**：原点在桌面中心正下方的地面，+Z 向上，单位 m、rad。
- `TABLE`：尺寸、高度、板厚、腿尺寸、摩擦。
- `ROBOT`：机器人资产（`robots/<name>`，描述取自其 `robot.py`）、底盘位置与偏航、起始关节（未列出的为 0）。格式上可以有多个机器人，环境目前只支持一个。
- `OBJECTS`：`{名字: {'asset': 'objects/<类别>/<编号>'}}`。尺寸、碰撞几何、关节都从资产读取，场景里不手写。场景原样引用资产的构建产物，不缩放、不覆盖质量、材料或驱动。
- `VIEWS`：录像用的固定视角，渲染时与机器人相机一样按名字选用。
- `IMAGE_VIEW`（可选）：构建初态图片默认用的视角，取 `VIEWS` 中的名字；不设时用机器人的主相机（`robot.py` 中第一个 RGB 相机）。
- `initialize(layout)`：随机初始化（布局 0），见下节。
- `LAYOUTS`：可选，同一批物体的其他摆法（布局 1、2、…），见[布局](#布局)。

资产按结构接入 Isaac Lab：带 articulation root 的资产（抽屉柜）是一个 articulation；刚体之间有关节但没有 articulation root 的资产（笔帽靠钢珠卡在笔身上）整体加载，每个刚体各是一个 rigid object。这样 Isaac Lab 的状态读写和录制覆盖每个刚体。物体刚体的名字取自资产的 `table1000:name`，特权状态里写作 `<物体>:<刚体>`（如 `cabinet:cabinet.drawer3`）。

## 随机初始化

`initialize(layout)` 用 `layout.rng` 抽样，写出各物体的位姿（资产坐标系）和关节值。同一 seed 必须得到同一结果，不能用其他随机源。接口分三层，场景按需选用：

| 层 | 接口 |
| --- | --- |
| 状态 | `set_pose(物体, 位姿, on=支撑)`、`set_joint(物体, 关节, 值)`：直接写入，无约束；支撑可以是桌子、物体或桌旁地面 `'floor'`（地上的物体，以及放在地上物体里的东西，比如地上垃圾桶里的垃圾，不算掉下桌） |
| 几何查询 | `surface_height(on)`（支撑面高度）；`resting_pose(物体, xy, yaw, on)`（离给定朝向最近的稳定放置朝向与高度，由碰撞凸包和资产显式给出的质心算出）；`penetration(物体, 位姿)`（与桌子和已放物体的穿透深度）；`geometry[物体]`（部件包围盒、关节轴等） |
| 便捷组合 | `place(物体, region, yaw, on)`：在区域内均匀采样原点位置（偏航可给范围），放到稳定朝向，与已放物体穿透就重采；`drop(物体, xy, yaw, rotation, frame)`：从上方竖直落下，停在最先碰到的桌面或物体上（落进容器、抽屉，叠到本子上），返回位姿和支撑；`scatter(物体, region, yaw, rotation, frame, onto)`：在区域内采样落点，直到落在 `onto` 指定的支撑上且整件物体在桌面范围内；`row(物体列表, start, direction, yaw, gap, frame)`：沿一个方向把物体按碰撞外形依次排成一行，间隔 `gap` |

多个场景共用的摆放组合在 `table_1000/scenes/arrange.py`：`stand_in`（立放进笔筒等容器）、`into`（随机落进容器）、`line_up_in`（在容器里排成一行）、`drawer_contents`（放进抽屉柜的某个抽屉，再推到给定开度）、`strew`（撒在一片区域）等。`drawer_contents` 适用于按约定命名的抽屉柜：刚体 `<类别>.housing` 与 `<类别>.drawer<i>`（1 为最上层），抽屉部件 `front`、`side1`、`side2`、`bottom`，滑动关节 `<类别>.drawer<i>.slide` 向 −Y 拉出；抽屉内可放的范围由这些部件的几何算出（两侧板之间、拉出部分里上层拉手之前）。

区域、落点和朝向可以在某个已放物体的坐标系（`frame`，只取它的偏航）中给出，例如笔筒内的落点、抽屉拉出部分的范围。几何随 `set_joint` 设定的关节值变化：拉开的抽屉按拉开后的位置参与穿透和落点计算。

`drop` 与 `scatter` 放下的物体是**松放的**：刚接触支撑，未必已经放稳（斜靠在笔筒壁上的笔）。`layout.free_landing = True` 表示松放物体可以落到任何地方（凌乱桌面上笔从笔筒里倒出来也算合理）；默认要求它们留在原来的支撑上。

框架在最后统一检查（`table_1000/scenes/initial.py`）：

1. **无穿透**：已放物体之间、物体与桌面之间按碰撞几何检查，接触允许，穿透不超过 1 mm。
2. **落稳**（有松放物体时）：复位后静置 3 s。松放物体可以移动，但着地点（最低 2 mm 内碰撞点的中心）要留在托着它的物体上（沿支撑链找到第一个非松放的物体，如容器或桌面，在其碰撞包围盒的水平范围内，关节取摆放时的值，拉开的抽屉也算）；`free_landing` 时不限。其他物体按下一步的限值检查。任何物体都不能掉下桌面，机器人不碰任何东西。
3. **静置稳定**：机器人保持不动、再静置 1 s。每件物体的每个刚体相对其支撑（桌子即世界）平移不超过 3 mm、转动不超过 2°，包括非 articulation 的笔帽和钢珠；物体关节变化不超过 3 mm（或 rad），机器人不碰任何东西。比较位置而不是速度：笔帽钢珠有微米级抖动，笔永远不休眠，但不会移动。

不通过就换下一个子 seed（`default_rng([seed, attempt])`）重新运行 `initialize`，最多 20 次，并记录每次的原因。`default_rng` 对整个列表做哈希，子 seed `[s, k]` 与其他 seed 的序列互不重叠。

通过的初态存进 `initial_states.hdf5`：每个有效 seed 一组，名称为 seed，属性 `seed`、`attempt`，内容为静置后的场景状态（格式同轨迹的 `initial_state`）；文件属性记录场景、机器人、物理后端和提交。专家轨迹从这些状态开始，不再重新采样；同一 seed 的摆放由代码确定，静置后的状态可能有微小差异，所以初态以文件为准。

例：笔的资产原始朝向是一个棱顶朝下，直接平放会滚动 7.5° 到相邻的面上，静置检查因此不通过；`resting_pose` 改用最近的稳定朝向后，静置移动降到 0.4 mm、0.2°。

## 布局

一个布局是同一批物体的一种摆法，由一个摆放函数给出；状态由布局号和 seed 确定。布局 0 是 `initialize`，其他布局在 `LAYOUTS` 中按编号给出：`{编号: {'quality': 'good' | 'bad', 'description': 英文说明, 'arrange': 函数}}`。`arrange(layout)` 与 `initialize` 用同一套接口写出位姿和关节，同样从 `layout.rng` 取随机数（落进容器、撒在一片区域的位置），经过同样的检查和重试；不同 seed 得到同一摆法的不同变体。`quality` 标明这是整理得好的还是差的方案，`description` 写明怎么摆，供人评与模型评价对照。编号定下后不再改动，新布局用新编号。

整理评测用的好坏布局：好的布局之间应在分组、收纳位置或排列方式上有明显区别；差的布局物理上可行，但整理质量差（堆成一堆、放错容器、只整理了一半）。这些布局不需要配套轨迹。

布局 n 的构建结果在 `layouts/<n>/`，文件和格式与布局 0 相同；`initial_states.hdf5` 的文件属性另记 `layout`。

## 专家程序 `expert.py`

定义 `solve(ctx)`：阻塞式代码，每个动作执行完才返回。`ctx` 提供：

| 层 | 接口 |
| --- | --- |
| 运动原语（与物体无关） | `ctx.solver(arm)` 的 `move_to_pose_with_RRTConnect`、`move_to_pose_with_screw`、`open_gripper`、`close_gripper`、`first_reachable`（依次尝试候选目标）；规划世界 `add_table`、`add_object`（由碰撞几何生成，可按部件分组）、`allow`（允许手指接触某部件）、`attach`/`detach`（手中物体）、`carry`/`release`（随手移动的关节部件，如被拉的抽屉）；`ctx.hold`、`ctx.step` |
| 状态与几何查询 | `ctx.pose(物体, 刚体)`、`ctx.joint(物体, 关节)`、`ctx.center_of_mass`、`ctx.part_box`（部件在刚体坐标系中的包围盒）、`ctx.geometry[物体]`（部件包围盒、关节轴）、`ctx.tcp()` |
| 抓取几何 | `table_1000.experts.grasps`：`build_grasp_pose`、`compute_grasp_info_by_obb`（ManiSkill 的同名函数）、`standoff`、`translated` |
| 原子技能 | `table_1000.experts.skills`（见下文）：`grasp`、`pick`、`move_by_displacement`、`push`、`release`、`place`、`make_room`、`ready`、`retry`；动作链 `chain`（`Pick`、`Place`） |
| 语义技能 | `table_1000.experts.skills.semantic`（见下文）：`open`、`close`、`place_on`、`place_inside`，谓词 `on`、`inside`、`is_open`、`is_closed` |
| 子任务 | `with ctx.subtask('put the pen into the drawer'):` 标记这段步数属于哪条英文指令 |
| 随机 | `ctx.rng`：需要变化的选择（抓取位置、顺序）用它，不用其他随机源 |

要求：

- 每个目标位姿由物体**当下**的实际位姿和资产几何算出，不按 seed 或固定世界坐标写特例。
- 手指只在需要的动作里允许接触相应部件；接触结束后撤销。例：先允许碰把手再用 RRTConnect 去把手前方，路径可能穿过把手，把抽屉推回去后抓空；应只在最后的直线接近时允许。
- 可以重试，但要写明候选（后撤距离、抬起高度；物理上等价的抓法与放法，如对称的手腕转向、绕圆柱轴侧倾、物体放置的两个方向）或次数上限（重新抓取），用 `ctx.note` 记下换用的候选。其余失败用 `ctx.fail(原因)` 或规划异常结束，记录子任务与原因。
- TCP 约定：+X 为接近方向，+Y 为手指张开方向。

规划用 MPlib（ManiSkill 也用它）：自由空间用 RRTConnect 到 IK 解，规划路径按 1 cm 关节步长复查碰撞，不过就重新规划；接触动作用直线 screw 路径。规划好的路径每个控制步（25 Hz）发送一个关节位置。RRTConnect 规划时碰撞几何膨胀 1 cm；膨胀导致端点重叠的物体在这次规划中用真实几何检查，不能因此豁免整条路径上的接触。路线简化与时间参数化后的轨迹也必须通过真实几何复查；时间参数化切过拐角时，保留原路线并在拐角停下。底盘移动后，规划世界随之更新坐标系。

抓取闭合后，用实测物体与手的位姿复核候选原有的最小夹持区域条件，同时检查闭合开度；物体在接近或闭合时移动后，原来的预测区域不再足够。未达到条件时按原有上限退出重抓。几何检查不能代替物理稳定性，pick 仍检查物体实际抬起。

抓取在当前站位无法完成接近后，请求底盘让位必须选择另一个站位；目标位姿有 IK 解，不能作为保留这个已失败站位的理由。主动调用 `make_room` 仍允许在满足请求时留在原位。让位与筛选的实际成本计入运行耗时，筛选上限和单次求解预算不因此改变。

### 分层

专家程序写在四层之上，每层只回答自己的问题：

| 层 | 回答 | 不管 |
| --- | --- | --- |
| 专家 `expert.py` | 物体要到哪、按什么顺序；有语义的中间状态（如先拉开抽屉再取笔）；每步的成功判据（谓词）；风格提示（如笔从桌上斜着拿起、放在桌上哪一侧） | 用哪只手、底盘站在哪、手臂何时收回 |
| 语义技能 `skills.semantic` | 把目标翻译成约束：放置区域与禁放区、把手与拉动方向、关节开度；判断目标是否达成的谓词 | 怎样满足这些约束 |
| 原子技能与动作链 `skills` | 在约束下选手、握法、交接、躯干和底盘：另一只手只在挡路时收回，底盘只在够不到时移动；前后相连的动作用 `chain` 连起来，下一步的需要（如握法要能把笔放进抽屉）在上一步就作为约束 | 物体该放到哪 |
| 运动原语（MPlib） | IK、RRTConnect、直线 screw 运动、执行 | 任务语义 |

专家不调用 `ready`、`make_room`，也不指定手臂。场景里先挪开哪个物体、挪到哪，仍由专家决定。

### 原子技能

`table_1000.experts.skills` 在运动原语之上提供以物体为单位的技能，接口仿照 RoboTwin 2.0 的任务 API，但和 `solve` 一样阻塞：每个调用在仿真中执行完、检查结果后才返回，做不到时以 `ctx.fail`（原因如 `no reachable grasp`、`object not held`、`no placement`）或规划异常结束；什么都够不着（没有可行的抓取、推或放置）时异常类型为 `Unreachable`。技能按物体的实时位姿和资产几何自己选择手臂、抓取候选和路径，每次换用候选都用 `ctx.note` 记下。选择时尽量少动身体，先尝试躯干不动的手臂动作，再考虑躯干和底盘。共享升降会带动两只手臂；抓取选择和允许升降的自由空间转移之前，先把会随之移动的空闲手臂收回到机器人声明的 `ready` 臂姿态（没有声明时沿用初态），持物的手臂不收回。收臂本身也必须经过规划与执行，不能直接改变关节配置。可移动躯干的 RRTConnect 在终点躯干高度不变时先锁住躯干规划，不通再放开。躯干和底盘的每次移动用 `ctx.note` 记下（`torso moved`、`base relocated`），`scripts/experts/resource_stats.py` 从批次的 `episodes/*.json` 汇总每条轨迹的次数与行程。

| 技能 | 作用 |
| --- | --- |
| `grasp(ctx, 物体, 部件)` | 抓住物体或其一个部件（如把手）。可给接近方向 `approach`、与它的最大夹角 `max_angle`（给一组时依次放宽，够不着才用下一个）、抓住后的位移 `then`（候选须让这段位移也有 IK 解）。先试肩部离物体近的手臂；闭合后没夹住（手指间隙小于物体宽度）就退出重选，至多 `MAX_REGRASPS` 次；可达范围内没有候选时先移动底盘 |
| `pick(ctx, 物体)` | `grasp` 后抬起 `height`；物体没跟着抬起时松手并失败（`object not lifted`） |
| `move_by_displacement(ctx, 手臂, x, y, z)` | TCP 沿直线移动。`drag` 指定随手移动的关节部件（拉抽屉）；`least` 允许整段规划不通时只走一部分，返回走过的比例 |
| `push(ctx, 物体, 部件, direction, distance)` | 闭合指尖抵住部件的面推动（推抽屉关上）；都够不着时先移动底盘 |
| `release(ctx, 手臂)` | 张开手指并沿接近方向退出 |
| `place(ctx, 物体, region, near, keep_out)` | 把手中物体放在表面上的矩形区域内：`region = (表面坐标系, 低角, 高角)`，表面为坐标系的 z = 0 平面；朝向不限，按离 `near` 的距离、再按转角排序采样；物体轮廓避开 `keep_out` 矩形。可达范围内没有可行位置时先移动底盘 |
| `make_room(ctx, 位姿)` | 移动底盘到能以关节余量够到给定 TCP 位姿处：当前位置够得到就不动；否则在位姿周围按距离和朝向采样底盘位姿，取机器人在该处及途中不碰桌子（含桌腿）和物体、最快到达的一个。先检查原地转向、直行、原地转向；起始转向受阻时，再检查沿当前朝向走到目标投影处后转向目标的局部路线。空闲手臂挡路时先收回并重新检查，仍不通就失败。完整机器人和持物都须沿途安全，不承担绕障导航。`path=True` 表示这些位姿是一条直线运动上的连续位姿；不给位姿时回到起始位姿。机器人没有底盘时不动 |
| `chain(ctx, 动作)` | 依次执行动作（`Pick(物体, ...)`、`Place(物体, 区域, ...)`，参数同 `pick`、`place`，`instruction` 给出时在该子任务下执行）。每个动作先满足下一个动作的需要：放置需要物体在某只手里、以能放到区域内某处的握法拿着（`InHand`），拿起时只选这样的抓取；够不着这样的抓取（`Unmet`）时，按 `adapt`（默认先交接再底盘）补救：近手拿起后交给另一只手，或允许移动底盘再拿。`Place` 的区域可以是函数 `region(ctx) -> (区域, keep_out)`，在执行时按当时状态求 |
| `ready(ctx)` | 空着的手臂回到机器人声明的 `ready` 臂姿态；没有声明的关节沿用初态，不改变躯干高度 |
| `retry(ctx, 步骤)` | 每次失败后先归档失败分支，再恢复回调入口的场景、控制指令、持物和规划状态，以新的随机数重试；`run_expert.py --skill-attempts K` 指定包括第一次在内的次数上限。`Unreachable` 也可重试，`Unmet` 交给动作链适配，程序错误直接抛出 |

底盘为连续动作选位时，要求同一关节分支能完成实际的直线运动，并检查整段的关节余量；各终点分别有 IK 解不足以证明动作可行。抓取后到放置前的自由空间转移另行规划，不要求走直线。直线动作执行了一部分后改用躯干补足时，以入口的绝对终点为准，仅完成剩余位移，不能重复整段位移。放置的需求筛选与执行均保留已采样的 release IK 分支，检查哪些分支能在同一躯干高度到达上方；不能仅因距离当前配置最近的分支失败而丢弃同一个放置候选。

自由空间路线的简化和时间参数化也必须保持碰撞与 URDF 关节位置约束。样条切弯或越过位置限位时，改沿已经验证的分段路线停靠拐角；仍不合法就报告失败，不截断越界指令。

### 语义技能

`table_1000.experts.skills.semantic` 在原子技能之上，按场景里的说法给目标：哪个物体、哪个关节、放到哪个表面。参数都从资产的碰撞几何和关节推出，不依赖具体场景。关节用资产 `model.json` 里的名字（如 `cabinet.drawer1.slide`）。场景 [000002](../../../asset_sources/scenes/000002/expert.py) 用这些技能写成。

| 技能 | 作用 |
| --- | --- |
| `open(ctx, 物体, 关节, 开度)` | 拉动方向取关节轴（随子刚体的实时位姿），把手取关节子刚体上名为 `handle` 的部件。正对把手抓取，与正对方向的夹角按 `OPEN_ANGLES` 逐级放宽；沿关节轴拉到开度后松手。拉不到位就分段重抓，至多 `PULLS` 次；拉动失败先松手。已经打开（差距不超过 `OPEN_TOLERANCE`）时什么也不做 |
| `close(ctx, 物体, 关节)` | 用闭合的指尖沿关节轴反向推把手，推过闭合位 `PUSH_PAST` |
| `place_on(ctx, 物体, 表面, 部件, near, keep_out)` | 把手中物体放在桌面（`'table'`）、某个物体或它的刚体、部件的顶面上，避开 `keep_out` 矩形，离表面边缘至少 `EDGE`（0.04 m，给之后拿起它的手指留空间）；给了 `near` 时只在它周围 `NEAR` 以内找位置 |
| `place_inside(ctx, 物体, 容器, 部件)` | 把手中物体放进容器（如一个抽屉刚体）的内底上没有被遮住的部分 |
| `on_region(物体, 表面, 部件, near, keep_out)`、`inside_region(物体, 容器, 部件, near)` | 返回函数 `where(ctx) -> (区域, keep_out)`：按调用时的状态求上面两个技能用的放置区域和禁放区，可直接作为 `Place` 的区域（如 `chain` 里拿起后放进抽屉，拿起时就按它选握法） |

**放置区域**：在支撑物上方按 `SUPPORT_STEP` 的网格竖直向下打射线，射线对场景中所有碰撞形状（桌面、各物体，不含要放的物体）求交。网格取支撑物所在刚体的坐标系。首先击中支撑物朝上面的格子，按高度归层：`place_on` 取最高的一层，`place_inside` 取最低的一层（内底，而不是边沿）。这一层格子的外接矩形（边界取在格子之间）就是放置区域。矩形内首先击中别的东西的格子，用击中刚体在自身坐标系下的碰撞包围盒作为禁放区：支撑物自己的其他部件按部件算，别的物体按刚体算。`place` 让物体从上方竖直放下，比物体下落时扫过的高度（物体高度 + `PLACE_CLEARANCE` + `PLACE_ABOVE`）还高的东西既不遮挡支撑面，也不列为禁放区，手臂是否碰到它由放置时的 IK 和规划检查。效果是：桌上立着的柜子和拉出的抽屉自动避开；抽屉只取露在柜体外的那段内底（柜内的隔板比下落高度低，仍然遮挡），悬在边上的上层把手不占区域。区域和禁放区随后交给 `place`。

**谓词**：

| 谓词 | 判断 |
| --- | --- |
| `opening(ctx, 物体, 关节)` | 关节离闭合端（下限）多远 |
| `is_open(ctx, 物体, 关节, 开度)`、`is_closed(ctx, 物体, 关节)` | 开度达到要求（容差 `OPEN_TOLERANCE`），或在闭合端 `CLOSED` 以内 |
| `on(ctx, 物体, 表面, 部件, keep_out)` | 从物体中心向下，首先击中的是该表面；物体最低点高出击中点不超过 `ON_TOLERANCE`；中心不在 `keep_out` 内 |
| `inside(ctx, 物体, 容器, 部件)` | 从物体中心沿容器刚体的 ±x、±y 和向下打射线，都击中该容器部件 |

语义技能结束时用谓词检查结果，不满足就 `ctx.fail`；专家的 `Step.check` 也用它们（`require(ctx, 谓词, 原因)`）。每个语义技能都在 `retry` 下执行（见[失败重试的轨迹语义](#失败重试的轨迹语义)）；它是有限兜底，`Unreachable` 只说明这次搜索未找到解，确定性的失败仍应修根因，不靠增加次数。辅助函数：`travel(ctx, 物体, 关节, margin)` 返回关节子刚体从当前位置拉到全开所扫过的矩形，`body_box(ctx, 物体, 刚体, margin)` 返回一个刚体的包围盒矩形，都可作为 `keep_out`（如笔不放在抽屉拉出的路径上）。

限制：
- 只支持滑动关节。转动关节（柜门）需要以下几项：沿圆弧拖动把手（现在的 `move_by_displacement` 只走直线）；开门过程中，抓取的接近方向随门转动；关门的推动方向随门面法向变化。
- 把手按部件名 `handle` 查找。
- 射线只从上往下打：被低于下落高度的部件盖住的支撑面（柜子内部的隔板）找不到；高于下落高度的遮挡只交给 IK 排除，候选位置可能因此偏向手够不着的地方。
- 网格对齐支撑刚体的坐标系，假定它的 z 轴朝上。

### 步骤

专家可以把子任务分成步骤：`Step(名字, run, check)`，`run(ctx)` 执行其中的子任务，`check(ctx)` 检查结束状态是否满足下一步的起始条件，不满足就 `ctx.fail`。步骤之间手里不拿东西。步骤列表定义为模块级的 `STEPS`，`solve` 写成 `run_steps(ctx, STEPS)`（`run_expert.py --steps` 据此选择步骤）。

### 逐步运行

由步骤组成的专家，每一步通过 `check` 后保存一个检查点：完整场景状态（`InteractiveScene.get_state`，格式同 `initial_state`：物体位姿与关节，机器人的底盘、躯干、手臂和夹爪）和各动作项保持的指令（`state/targets/<动作组>`：关节目标、夹爪的指令开口、底盘速度；夹着东西的夹爪指令开口小于实际开口，靠这个差保持夹紧，恢复时一起写回），以及该 seed 回合开始时机器人的关节和底盘位姿。一批的检查点按步骤存为 `checkpoints/step<k>.hdf5`，从初态开始的批次另存 `step0.hdf5`（初态，名字为 `initial state`），每个 seed 一组（属性 `seed`、`attempt`、`at` 即这一步结束时的控制步；`state`、`start`），文件属性记录场景、机器人、后端、提交、步骤序号和名字。

不带参数的 `run_expert.py <场景>` 生成场景的数据：所有 seed 从初态跑完所有步骤，替换 `data/scenes/<场景>/<后端>/`。`--dev` 是开发运行：写到新目录 `runs/expert/<场景>/<日期>-<时间>-<提交>[-<--name>]/`，格式与数据相同，以后的运行不会替换它；`summary.json` 的 `run` 与 `command` 记录运行名与命令行。只跑部分步骤或 seed 的运行都是开发运行，须带 `--dev`。

`run_expert.py <场景> --dev --steps k[-m]` 只运行第 k 到 m 步：k 为 1 时从初态开始；k 大于 1 时须给 `--from <批次目录>`，从那一批第 k − 1 步的检查点开始，先静置 0.2 s（k 为 1 时也可以给 `--from`，从那一批的 `step0` 开始，与从初态开始相同）。有检查点的 seed 都会运行（`--seeds` 只运行其中给出的，初态同样适用），输出格式与完整批次相同，并写出新的检查点。恢复后，空闲手臂回到的姿态和底盘的起始位姿仍取该 seed 回合开始时的，而不是检查点处的。从第 k 步开始时 `ctx.rng` 为 `default_rng([seed, attempt, 1, k])`，MPlib 的随机数也随 k 改变。`--dev --repeats K`（默认 1）让每个 seed 从同一起点跑 K 次，每次换一组随机数（`ctx.rng` 与 MPlib 的都换），第一次与不加该参数时相同：得到每个 seed 从该起点完成这几步的成功次数，用来区分换随机数就能过的失败和结构性的失败。其余各次的报告为 `episodes/<seed>-<r>.json`（r = 1 … K − 1），不录轨迹、不写检查点；批次的成功率等仍按第一次计，`summary.json` 的 `repeats` 给出每个 seed 的成功次数（满分 K）、各失败原因在每个 seed 上出现的次数、全部运行的成功率，以及因进程中途退出而少跑的 seed 与其实际次数（`short`；进程退出时只重跑还没有第一次结果的 seed）。

`summary.json` 的 `steps` 给出每步的起始 seed 数、完成数、成功率（完成 / 起始）和逐步完成率（progressive completion rate，ManiSkill-HAB 的统计方式：这一步及之前各步都完成的 seed 占第 1 步起始 seed 的比例）；从检查点开始的批次沿用来源批次前几步的行，分母也取来源批次的。每条轨迹的 `episodes/<seed>.json` 记下每步结束时的控制步数、专家的墙钟秒数和进程的 CPU 秒数（`steps` 的 `at`、`wall_s`、`cpu_s`）与每个子任务的墙钟秒数（`subtask_wall_s`）；`scripts/experts/step_times.py` 按步骤和子任务汇总批次的仿真时长、墙钟时间和规划耗时。

`join_steps.py <批次> ...` 把逐步运行的各批按顺序接成完整轨迹，默认写成场景的数据 `data/scenes/<场景>/<后端>/`：拼接的轨迹与一次跑完的完整轨迹只是生产方式不同：每段在下一批开始用的检查点处截断，接上下一批同一 seed 的轨迹，`subtasks` 和 `steps` 平移到接好后的位置，`parts` 记录每段的批次、提交、步骤、起点和长度。每个 seed 的 `episodes/<seed>.json` 取最后一段的报告并平移到接好后的位置，`summary.json` 按同样的方式统计成功率和失败，所以输出目录的格式与一批轨迹相同，可直接渲染、分析失败案例。只有所有 seed 跑完所有步骤的拼接才默认写成场景的数据，否则须给 `--output`。逐步迭代的方法见[操作手册 05](../../tutorials/05-step-by-step-expert.md)。

拼接报告保留最后一段的 `call_trace`、`solve_trace`，对应文件复制到新批次。帧号和数值记录不改写；`call_trace_offset` 是原记录控制步到拼接轨迹的偏移，`read_trace` 自动平移帧的 `enter`／`exit`。原帧 `enter=0` 的入口状态另存为 `call_trace_initial_state`（`calls/<seed>-initial.hdf5`）：恢复取该段自己的初态，避免用前一段末状态替代；其余入口取拼接轨迹的 `states[enter-1]`，控制指令取帧的 `targets`。再次拼接会累加偏移并携带入口状态。求解记录中 `operations.step` 仍是原段内下标，可加同一偏移换算；离线数值重解不依赖它。

拼接结果不合并此前各段的调用树、求解记录或后续 repeats；需要分析这些记录时使用来源批次。最后一段没有保存求解记录时，拼接不会补采集。

`run_expert.py --profile`（默认关闭）在报告里增加嵌套 wall 计时：`wall_profile` 是整条专家运行的分类统计，步骤的同名字段是累计快照，`subtask_profiles` 与 `subtasks` 一一对应。每类有 `calls`、包含已计时子调用的 `wall_s`、扣除这些子调用的 `self_s`；只有 `self_s` 能跨类别相加。抓取候选、IK、RRT、轨迹时间参数化、显式碰撞、路径验证、世界更新、底盘和交接搜索、控制步进分别计时；控制步进中的动作转换、物理与录制另记为 `physics_step`，因此步骤和子任务也有此项分解。MPlib 内部的碰撞检查仍包含在 IK/RRT 中；RRT 的自身时间还包含原生路径简化和 Python 包装。惰性候选生成器只计每次恢复执行，`calls` 包括最终耗尽的一次，不是候选数。`timings.physics_step_s` 是控制步进中动作转换、物理与录制的耗时，不含观察与模型同步，不能再与分类的 `self_s` 之和或 `control_step.wall_s` 相加。`step_times.py` 输出每条的平均自身/嵌套耗时及未覆盖的专家时间，仍兼容未开启计时的旧报告。`eval_pick.py --profile` 同样记录每个 trial 的 `wall_profile` 和 `physics_step_s`。

开启 profile 时，各项同时记录调用线程的 `thread_cpu_s`、`self_thread_cpu_s`，与 wall 的包含/扣除子调用规则一致。Linux 上还尝试用 `perf_event_open` 记录当前线程用户态的 retired instructions（`instructions`、`self_instructions`，不继承到工作线程）；计数器固定在硬件上，无法调度或读取时直接报错，权限不允许打开时在 `profile_counters.instructions` 记录原因并省略指令字段。未开启 profile 时不打开或读取这些计数器。多线程的 `physics_step` 只公开 wall 与区间内整个进程的 `process_cpu_s`，包括动作、物理和录制，也可能包含同时运行的后台线程；它不能与其他类别的线程 CPU 相加。父项仍扣除该区间的调用线程 CPU/指令，避免计入控制其余工作。`profile_totals` 给出录制区间的 wall、线程 CPU、可用的指令数，以及进程口径区间内被排除的线程量（`process_spans_*`），用于计算未包裹的工作。步骤和子任务沿用同一套字段；`step_times.py` 展示各口径，缺失测量显示 `-`，不会作为零参与新口径的均值。线程 CPU 不包含库的工作线程；需结合具体库的执行方式和线程配置解释，不能视为整进程 CPU 或消除 RRT 墙钟时限导致的工作量变化。

当前 MPlib 0.2.1 的 IK、FCL、RRT 搜索与 TOPP 在调用线程同步执行；使用单线程 BLAS 时这些计算由线程 CPU 覆盖。其 OMPL 1.6 在规划预算不少于 1 s 时另开检查终止期限的辅助线程：该线程不执行搜索，但其 CPU/指令不进入调用线程的分类，CPU 仍计入 episode 的进程 `cpu_s` 与负载采样。Isaac 后台线程在规划期间运行的 CPU 同样只进入进程总量，不应归到 RRT/IK 的线程 self 时间。

## 轨迹数据

**无图片、可重放**：直接使用 Isaac Lab 录制器的 HDF5（`trajectories.hdf5` 存成功的，`trajectories_failed.hdf5` 存失败的）。每条轨迹 `data/demo_<seed>`：

| 内容 | 说明 |
| --- | --- |
| `initial_state` | 静置后的场景状态（`InteractiveScene.get_state`：每个 articulation 的根位姿、速度、关节位置与速度，每个 rigid object 的位姿与速度） |
| `actions` `[T, A]` | 每个控制步的动作；各动作组的区间见文件的 `env_args.action_layout` |
| `states` | 每步之后的场景状态 |
| `obs/*` | 每步之前的机器人观测（`qpos`、`qvel`、`base_pose`、`tcp_<arm>`） |
| 属性 | `scene`、`seed`、`attempt`、`instruction`、`subtasks`（每段的指令与起止步）、`status`、`failure`；由步骤组成的专家另有 `steps`（完成的步骤及其结束的控制步）和 `from`（开始用的检查点文件，从初态开始时为空） |

`env.reset_to(initial_state)` 后依次执行动作可在物理中重放；`scene.reset_to(states[t])` 精确恢复第 t 步，用于渲染。每条轨迹开始前用 seed 设置 MPlib 的随机数（`mplib.pymp.set_global_seed`），专家的 `ctx.rng` 为 `default_rng([seed, attempt, 1])`；RRTConnect 有规划时限，负载不同时路径仍可能不同。

一批轨迹的进程各自录制，结束时按 seed 顺序合并成一个 `trajectories.hdf5` 和一个 `trajectories_failed.hdf5`。每条轨迹另有报告 `episodes/<seed>.json`：子任务起止、每次规划、手指碰过的部件、换用的候选、失败原因、物体终态与耗时。

**渲染**：`render.py` 按状态逐步恢复并渲染指定的相机（机器人的 RGB 相机或场景的固定视角），不推进物理。每一步：`scene.reset_to(states[t])`；调用 PhysX 的 `update_transformations` 把位姿写进 USD（不推进物理时渲染器读不到新位姿）；渲染一次。RT2 在时间上降噪，相邻控制步只差 40 ms，混入的上一帧与收敛画面的平均像素差不到 2（0–255）；每条的第 0 帧接在另一条轨迹之后，多渲染几次。T 步的轨迹录像为 T 帧，第 t 帧是第 t 步动作之前的状态，与 `obs[t]`、`actions[t]` 对应。录像与轨迹放在同一目录：成功的在 `videos/`，失败的在 `fails/`，每条轨迹一个目录，每个相机一条（`<seed>/<相机>.mp4`），或合成一条（`<seed>/merge.mp4`）；标注可选。每次只写本次渲染的录像，已有的其他录像保留；每个文件写完整后才放到最终位置，中断不会留下半成品。生成新批次时整个目录被替换，旧的渲染随之删除。

带图片的数据集（如 LeRobot）可以由 `trajectories.hdf5` 逐步恢复状态、渲染机器人相机得到，目前不在生产流程中。

### 失败重试的轨迹语义

`run_expert.py --skill-attempts K` 是每个 `retry` 回调包括第一次在内的尝试上限，默认 3，`K=1` 关闭这层兜底。重试先归档失败分支，再恢复回调入口的场景与控制指令、持物、规划世界及接触权限、当前子任务和放置需求，换一组随机数重来；第一次的随机数不受 K 影响。它不改变候选预算、碰撞条件或物理参数，也不重试程序错误。动作链里每个回调分别计次，K 不是整个场景的尝试次数。比较不同 K 时固定代码、初态与记录策略，并报告实测负载。

重试只覆盖回调内部：`open`/`close` 的动作及其内部检查会重试；`place_on`/`place_inside` 的放置结果检查和 `Step.check` 在回调外，失败即结束该次运行，不会重新抓取或重做整步。

主轨迹只保留连续的入口前缀与最后一次尝试，控制步及帧下标沿此轨迹计数，状态回滚不录成动作；物理时长只计算保留的动作，墙钟和 CPU 耗时包含被丢弃的尝试。丢弃的失败分支保存为主批次下的 `attempts/<seed[-repeat]>/<尝试编号>/`，格式同一个批次（轨迹、检查点、调用帧、求解问题和报告），可直接交给 `failure_snapshots.py`、`resolve.py` 与渲染工具；主报告的 `retry_archives` 列出所有分支，包括被外层重试再次丢弃的嵌套分支。`--problems failed` 下失败分支保留求解问题，`none` 两者都不保存。

归档中的异常属于抛出它的技能帧，之后成功的清理动作不改变它；回调自己的检查抛出的异常属于其控制帧。技能帧重放只执行该具体技能及快照指定的步骤检查，不在外面添加重试，也不重建上层回调闭包，所以单个技能返回成功不等于原回调成功。研究单帧随机性用 `--repeats`。

### 专家调用帧与失败恢复

每次运行另存 `calls/<seed>[-<repeat>].json.gz`，包括不录制场景轨迹的后续 repeats；每条报告的 `call_trace` 给出相对路径。帧树有步骤、子任务、技能三种帧，序号和父序号表示层次。每帧记录名字、实际参数、进入和退出的控制步、入口子任务与随机数、完整持物（手臂、Target 的构造数据、supports、grasp）、规划器挂载物体的相对位姿及允许接触，以及结果或异常（原因、details、是否 Unreachable）。体积由 gzip 压缩控制；场景状态继续共用录制轨迹，不在各帧重复保存。

恢复同时保留入口时规划世界所见的障碍物位姿和机器人配置。它们可能来自最近一次规划，与实时场景有差别；重跑使用原规划世界，避免在技能开始前刷新障碍物而改变原 IK 的输入。

技能入口 `enter = n` 的场景是已执行 n 个控制步后的状态：n 为 0 时取 `initial_state`，否则取 `states[n-1]`，并恢复入口的控制指令 `targets`。技能入口的 MPlib 种子由 seed、attempt、帧序号、repeat 派生并重设；入口同时记录 `ctx.rng.bit_generator.state`。MPlib 不提供可读的全局随机状态，因此帧入口是其随机数恢复边界。规划时间上限、物理接触及机器负载仍可能使结果不同。

retry、chain 和 Pick / Place / Handover action 都记录为技能控制帧；闭包只记录名字和实际发出的子调用，不持久化 Python 闭包。Place 给 pick / handover 的 `InHand` 保存已求值的区域、放置候选、可用手臂和已有判定，可重建原需求，不重新求区域。

`failure_snapshots.py <批次> [--frame 序号]` 默认选失败路径最内层、参数已求值的具体技能。步骤 check 失败时，选该步最后一次具体技能，重跑结束再执行该 check；显式选择控制帧时定位到其最后一次具体技能。快照保存技能入口的场景和执行状态，为新批次的 `checkpoints/step<k-1>.hdf5`。`run_expert --dev --from <快照批次> --steps k` 直接恢复并调用该技能；第 1 次使用原随机数，后续 repeats 换随机数。报告的 `replay` 区分原失败帧和原因是否相同，技能成功只表示该调用成功，不生成整步完成的检查点。遥操从 failure 起点使用相同的恢复，恢复持物等状态后交给人。

没有调用帧的历史批次仍支持 `--before` 的场景快照，专家从整步开头执行。详细命令见[教程 05](../../tutorials/05-step-by-step-expert.md)。

### 复用边界

环境与状态恢复使用 Isaac Lab 的 `InteractiveScene.get_state/reset_to`，静置检查复用 `RobotEnv.privileged()` 已从 Isaac Lab 刚体和关节数据取得的全量位姿。录制使用官方 `RecorderManager`、动作和状态 recorder、`HDF5DatasetFileHandler`；项目只补 agent 观测组与任务属性。

重放按 HDF5 行读取当前状态：官方 `HDF5DatasetFileHandler.load_episode` 会一次加载整条轨迹，渲染只需要当前状态。初始化的候选位置检查发生在写入仿真之前，并需与 MPlib 的规划碰撞几何一致，复用已有 FCL 与资产几何适配；稳定放置复用 trimesh。

抽屉滑动除有限次重抓外，另设每次调用的总动作次数上限，覆盖剩余行程小于滑脱容差的停滞；到达目标的最后一次动作仍可正常返回，超限用 `ctx.fail` 结束该轨迹，继续后续 seed。

## 验收

**自动化硬性检查**：初态无穿透、静置稳定（见上）。

**量化指标**（不设硬性门槛）：

- 初态（`initial.json`）：无法初始化的 seed、平均尝试次数、静置时的最大移动；
- 轨迹（批次的 `summary.json`）：成功率（分母为全部 seed），失败的 seed 按“子任务: 原因”列出，原因来自专家的检查（`ctx.fail`）、规划失败或专家代码出错，进程中途退出时没有结果的 seed 记为 `-: process exited`；什么都够不着（`Unreachable`）的 seed 另列在 `unreachable`，及其比例 `unreachable_rate`；成功轨迹的平均时长、每条墙钟耗时；
- 每条轨迹的报告：规划次数、换用的候选、手指碰过的部件。手指以外的接触不统计：密集摆放时手臂碰到物体是正常的。

**评审**：

- 初态拼图（`build_scene.py --grid`，默认机器人主相机），人工查看摆放是否合理、多样；最小有效 seed 的图缩小后作为场景缩略图提交；
- 前 5 条成功轨迹录制视频（机器人三个相机与 `wide` 视角合成一条，带标注），人工查看：流程完整，物体到位，手、臂与物体无可见穿模，夹持稳定，物体无异常滑移或跳动。失败的轨迹也录制视频（标注失败原因），用来判断是否值得修改专家。

批量运行从固定提交的独立检出进行（如 `git worktree add --detach`），运行期间不改代码、场景和资产；`initial.json` 与 `summary.json` 记下所用的提交和 seed，有未提交的改动时带 `+dirty`；`--root` 不是一个检出的根目录（如复制到别处的源码）时记为 `null`。

机器忙时墙钟会变长，所以轨迹记下运行时的负载，不要求在空闲时运行：`episodes/<seed>.json` 的 `load` 有机器名 `host`、机器的核数 `cores`（与平均负载一样按整台机器算），以及开始、结束和其间每 30 s 一次的采样 `samples`（`t` 秒、1 分钟平均负载 `load_1m`、距上次采样进程用掉的 CPU 秒数 `cpu_s`），`cpu_s` 是整条轨迹进程用掉的 CPU 秒数。CPU 秒数含仿真与规划的所有线程，可以多于墙钟；同一份代码在忙的机器上 CPU 秒数与墙钟之比更低。`summary.json` 的 `load` 汇总这一批：`hosts`、所有采样的“负载 / 核数”与各条轨迹“CPU 秒数 / 墙钟”的分位数（`p10`、`p50`、`p90`、`p100`）。三个脚本都分成 `--jobs` 个进程并行，本机平均分到 `--gpus` 列出的显卡上，或经 `--launcher` 交给作业调度器：seed 分成连续的段，要渲染的轨迹按帧数分配，每个进程一份；某个进程失败不影响其他进程，其中没有结果的 seed 按 `--retries` 重跑。不渲染时物理在 CPU 上，每个进程只占约 0.5 GB 显存，可以在一张卡上并发多个。轨迹的后端用 `--physics` 指定，命名与物理测试一致（`isaac-cpu`；场景生成尚未在 GPU 上验证）；初态固定用 `isaac-cpu` 生成。

## 已知限制

- 只在 CPU PhysX、单环境上运行；GPU 与多环境见 [issue #11](https://github.com/xucj98/table-1000/issues/11)。
- `surface_height`、`resting_pose`、`place` 的支撑面只有桌面和物体碰撞包围盒的顶面；放进容器、抽屉或叠放用 `drop` / `scatter`。
- `drop` 停在第一次接触的位置，物体未必放稳，由落稳检查交给物理决定最终位置；落稳后的状态以文件为准。
- 笔的帽与钢珠一直有微米级抖动，不休眠（不影响任务）。
- 摆放由 seed 完全确定，静置后的状态以 `initial_states.hdf5` 为准。专家轨迹：MPlib 的随机数按 seed 设置，但 RRTConnect 有规划时限，负载不同时路径仍可能不同。复现轨迹以录制文件为准。

### 离线求解问题

`run_expert.py --problems {failed,all,none}` 控制求解问题的保存范围，默认 `failed`：运行中照常记录，结束为失败或程序错误时保存 `problems/<seed>[-<r>].json.gz`，`episodes` 的 `solve_trace` 指向它；成功时不写文件，`solve_trace` 为 null。`all` 保存所有运行；`none` 关闭记录及额外 IK 诊断，`solve_trace` 为 null。repeats 和从帧恢复都按每次运行自己的结果判断；批次 `summary.json` 的 `problems` 保存所选模式。`calls/` 在三种模式下均照常保存。

人工遥操不安装求解记录器，`solve_trace` 始终为 null：控制循环每步执行的 IK 不属于专家的规划决策。调用帧与场景轨迹照常保存。

求解记录包含技能帧内的决策树、候选及筛选关卡，以及每次 IK、直线规划、RRTConnect 的数值输入与结果。候选按原来的惰性枚举顺序保存：未生成的后缀不展开，预算、接近角度、已尝试候选等停止条件单独记录。放置候选列表完整保存；需求的缓存命中也记录其原候选、握法和判定。

记录以 `frame` 关联调用帧树，以 `decision`、`candidate`、`stage` 关联筛选过程。`operations` 序号同时包含独立 IK、技能内部的路径筛选和运动求解；嵌套调用通过 `parent` 关联。每个问题包含完整机器人配置、底盘位姿、目标或关节 goals、求解预算和 lift，以及当时的规划世界：对象几何、世界位姿、挂载的相对位姿、允许接触和每个对象实际使用的 padding。IK 失败按决策与关卡汇总计数，前 5 个附带独立 CLIK 的无碰撞检查与碰撞对探测；探测结果用于诊断，不表示已穷尽所有 IK 解。结果包含状态、原因、路径长度、点数、运动时长和求解耗时；实际执行的运动另有跟踪误差。重复世界与几何共用，文件以 gzip 压缩。

`scripts/experts/resolve.py` 只使用 MPlib、机器人资产和记录，不启动仿真。可按批次、seed、帧、决策或规划序号选取问题。第一次使用原记录的技能种子并重放此前的求解调用以对齐随机数流，后续次数使用独立种子。每次求解都恢复该问题记录的测量状态；这衡量数值问题的成功率，不衡量物理执行成功率。RRTConnect 的时间预算仍受机器负载影响，调用前缀中的 RRT 也可能因此消耗不同的随机数。

`--redecide` 直接重新运行已求值的候选决策，复用专家的候选枚举、IK、需求和规划规则，继续检查新通过候选的后续关卡。运动路径按理想关节跟随更新规划模型，不计算接触动力学、跟踪误差或步骤完成谓词。其结果与单次问题的重解分别报告，不能替代从技能帧启动仿真的验证。没有求解记录时需先重跑采集；从失败技能帧快照重跑时加 `--problems all`，成功的重跑也会保留记录。采集结果及其来源应与原批次的失败区分。
