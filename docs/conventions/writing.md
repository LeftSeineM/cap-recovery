# 文档写法

## 分类

| 目录 | 读者 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| `research/` | 所有人 | 研究问题、交付物、计划、技术参考 | 实现细节 |
| `conventions/` | 所有人与 agent | 协作和开发规则，每条写明要求与原因 | 具体命令 |
| `tutorials/` | 人 | 交付什么、运行哪些命令、看哪些文件、怎样人工验收、典型值 | 字段与格式定义（链接到规范） |
| `specs/` | 编写代码和资产的 agent | 编写资产和专家的规则、跨模块的文件与格式约定、语义与不变量、已知限制 | 命令行用法、技能与函数的参数、实现细节、开发经过 |
| `decisions/` | 所有人 | 方案选择：最终方案、依据、适用边界、未采用的方案各一句 | 尝试过程、中间数据 |
| `experiments/` | 所有人 | 实验台账：问题、结论、提交、命令、结果，见[台账说明](../experiments/README.md) | — |

资产目录中的 `README.md` 只写模型结构、接口、必要参数、使用方法和已知限制，格式见[README 与缩略图](../specs/README.md#readme-与缩略图)。

## 原则

- 写当前状态：现在是什么、怎么用，不写变化过程（“原先……现在……”“修复了……”）。过程写在 PR 说明里，跨多次迭代的结果写在实验台账里。
- 每项定义只有一个权威来源，其他地方需要时写一句摘要并链接，不重复展开。目录用途只在[仓库与目录](repository.md#目录)，各资产文件的位置只在[资产布局](../specs/README.md#资产布局)，批量脚本的通用参数只在[操作手册](../tutorials/README.md#批量运行的通用参数)。
- 规范只写代码表达不了的：编写资产和专家时必须遵守的规则，生产方与消费方之间的文件和格式约定，分散在多处实现中的语义与不变量，已知限制。代码一改就要跟着改、又不是对外约定的内容（函数参数、算法细节、计时的内部类别），写在模块和函数的 docstring 里，规范链接到模块。报告中供其他模块或分析脚本读取的字段及其累计口径属于格式约定，留在规范里。实现原因与仿真器的坑写成代码注释。不与项目不使用的工具作比较。
- 手册一章一件事，篇幅以一屏为目标（约 60 行）。操作的前提、命令、结果和失败处理要写全，确实放不下时再拆章。命令多由 AI 运行，人看结果，所以验收章节按交付物组织：一句话和一张图；「交付物」表写有哪些东西、在哪；「验收」逐项写看什么（两三项，给典型值或判断标准）；「命令」集中放常用命令，其他参数让读者用 `--help` 查看；最后写不通过时改哪里。写给编写专家的过程章节按步骤写。字段含义写在规范里，某个资产的实测值写在它的 README 里。
- 规范和手册中的数值写成典型值或要求（“约 0.95”“不超过 3 mm”），不写“来自某提交的批次”“上一批失败的是……”。具体批次的结果写在 PR 说明里，需要时整理进台账。
- 用平实的陈述句直接写要求和结果。不写对比式的警句（“A 不能代替 B”“它回答……不回答……”“这不是……而是……”），不用加粗的句子当小标题。
- 英文更通用的术语直接用英文，如 commit、wall time、CPU time、sim time、RTF、seed、IK，不另造中文译名。
- 先给结论和最常用的用法，再给细节；一节只讲一件事，按读者使用的顺序排列。新增内容放进它所属的那一节，不追加在文末。
