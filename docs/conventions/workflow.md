# Issue、PR 与审查

## Issue

issue 是交给 agent 的任务书，用中文写。一个 issue 对应一个 PR，工作量约数个小时到一两天，一个从零开始的会话能接手完成。不开汇总清单式的 issue；跨多个 PR 的需求拆成父 issue 与子 issue。新 issue 先与项目负责人确认标题和范围再创建。

正文按 [issue 模板](../../.github/ISSUE_TEMPLATE/task.md)写：

- 背景：现象和数据（失败案例、批次结果），相关的 issue、PR。
- 目标：要达到什么，有哪些约束（如“不按资产写特例”）。
- 验收：命令、场景与 seed 范围、指标要求。
- 不做：范围外的事。
- 思路（可选）：已知线索、可参考的实现。

正文始终是当前的任务定义：讨论中改了目标或范围，同步改正文，评论只留讨论过程。实现结果写在 PR 说明和实验台账里，不写回 issue。

## PR

- 从最新 `main` 创建分支。每个 PR 聚焦一个可独立审查的改动，用 `Closes #N` 关联 issue。
- 跟进 `main` 可以 rebase；分支上有 commit 写进了实验台账时改用 merge（见[复现原则](../experiments/README.md#复现原则)）。
- 改动验证后可以直接提交并推送到 PR 分支；合并到 `main` 需要项目负责人批准。
- 说明写：要解决的问题、最终行为与用法、验证结果、已知限制。不写开发过程。
- 涉及成功率、耗时、物理指标或研究结论的 PR，说明中给出前后对比表（两边的 commit、seed 范围、关键指标、负载），并链接对应的[实验台账](../experiments/README.md)条目。台账条目随 PR 一起提交。
- 用 squash 合并，`main` 的每个 commit 对应一个完整的 PR。

## 审查

审查以正常使用流程能正确运行、结果可信、代码简洁为准：

- 只修正常使用会遇到、会给出错误结果或丢失数据的问题；轻微问题记录即可，不为假设的边界情况增加防御性检查、异常兜底或测试。
- 错误输入在底层自然报错的地方直接报错，不提前校验、不捕获。批量运行按 seed 隔离：某个 seed 出错时记录失败，其他 seed 照常运行。
- 测试只覆盖关键行为和已复现的实际问题。需要 Blender、Isaac 或生成资产的集成测试注明运行环境与输入，产物写入 `outputs/`。
- 操作手册按文档命令复现，并检查生成结果。修正后重新验证受影响的部分。
